# Windows competitor evidence for 0.1.2

This evidence measures the clean immutable implementation commit
`228f95227c49f0c750bbecb3d02d267c0ab45cf0`. The worktree was empty at the
start of both commands. The evidence-only documentation commit that adds this
file does not change the measured implementation or harness.

Environment:

- Microsoft Windows 11 Enterprise 10.0.26200, build 26200;
- Intel Core Ultra 7 255U, 14 logical processors;
- 50,992,144,384 bytes physical RAM;
- rustc 1.97.1 / Cargo 1.97.1, `x86_64-pc-windows-gnu`, release profile;
- Microsoft Defender antivirus and real-time protection enabled;
- Mago Text Edit 1.45.0, `ra_ap_text_edit` 0.0.241, typst-edit 0.1.0;
- three rotated warmups; 9, 15, or 31 measured samples according to workload.

Every adapter output was checked byte-for-byte against the independent
reference splicer before timing. The harness also asserts that the optional
Weavatrix rendered-output cache is cold for all primary rows.

The default-ceiling one-shot medians were 2.86 ms for Weavatrix and 2.83 ms
for Mago. Allocating prepared replay was 2.53 ms versus 2.63 ms. Preparation
was 303.40 us versus 38.50 us, but that row is deliberately ratio-free because
Weavatrix additionally validates exact `before` text, UTF-8 boundaries,
provenance, and hard budgets.

This matrix is not a universal 2x result. The equal-length caller-`String` row
is memory-copy-bound and rust-analyzer was about 9% faster in this run. The
same workload with a caller-owned `Vec<u8>` was 2.16x faster in Weavatrix, and
the same-offset Vec row was 2.33x faster. Mago caller-buffer replay was slower
than Weavatrix in every recorded String and Vec workload.
